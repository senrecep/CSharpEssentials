# CSharpEssentials.Endpoints: Performance Benchmarks

**vs. plain Minimal APIs, Carter 10.0.0, FastEndpoints 8.3.0 (+ FastEndpoints.Generator 8.3.0) · BenchmarkDotNet v0.14.0 · AMD Ryzen 5 5600 · .NET 8 / 9 / 10 / 11**

---

## What Was Measured

Four scenarios, each run against the same endpoint set in every library:

1. **Cold startup** (`ColdStartupBenchmarks`). A fresh process for every sample (`RunStrategy.ColdStart`, 15 launches, 1 iteration, no warmup). It runs the builder, services, `Build`, mapping, TestServer start, one `GET` to every endpoint, stop and dispose. JIT, assembly scanning, RequestDelegateFactory and each library's lazy first-request work all fall inside the measurement. **This is the like-for-like startup number.**
2. **Warm startup** (`StartupBenchmarks`). Mapping plus enumeration of every endpoint data source, in a process that the self-check and the warmup iterations have already warmed. No server is started. FastEndpoints defers its per-endpoint binder and validator setup to the first request, so its warm figure leaves that work out (see Caveats).
3. **Throughput** (`ThroughputBenchmarks`). One request through an in-process TestServer app with three routes: `GET /users/{id}`, `POST /users` (validated, valid and invalid body) and `DELETE /users/{id}`. The POST rows run on net10 and later only.
4. **Native AOT** (`benchmarks/endpoints-aot/run-aot.sh`, not BenchmarkDotNet). The same three-route app per variant, published with `PublishAot=true` for linux-x64 on net10. The script records IL warnings, binary size, time to the first 200, and whether all routes answer.

The startup scenarios use N = 10, 100 and 500 generated endpoints. Endpoint *i* is `GET /items{i}/{id:int}` returning `ItemResponse(id, "item{i}")` in every variant. The endpoint libraries are generated by `generate-endpoints.py`.

Variants:

| Variant | What it is |
|---|---|
| Plain | Hand-written `app.MapGet/MapPost/MapDelete` calls |
| CseGenerated | `IEndpoint` types mapped through the generated registry (`app.Map{Asm}Endpoints()`) |
| CseReflection | The same types mapped with the opt-in `MapEndpointsFromAssemblies` scanner |
| Carter | One `ICarterModule` per endpoint, `AddCarter` + `MapCarter` (net10 and net11 only; Carter 10.0.0 targets net10) |
| FastEndpoints | `Endpoint<TReq,TRes>` classes, reflection discovery (`AddFastEndpoints` + `UseFastEndpoints`) |
| FastEndpointsSourceGen | The same, with FastEndpoints.Generator discovered types |

The numbers come from the reports committed under `benchmarks/results/endpoints/{tfm}/results/` and `benchmarks/results/endpoints/aot/aot-report.md`.

## Executive Summary

Primary runtime: net10. "CSE" means CseGenerated unless the row says otherwise. Ties are differences within the sum of the two BenchmarkDotNet error margins.

| Finding | Details |
|---|---|

### 4. Native AOT (net10, linux-x64, three routes)

> Script-driven, not BenchmarkDotNet. Startup = ms from process start to the first 200 on `GET /users/1`, median of 5 runs after one discarded warm-up run. JIT = framework-dependent publish without `PublishAot`. Run at a load average of 2.84; startup numbers are sensitive to machine noise.

| Variant | AOT publish | IL warnings (distinct) | Native binary | JIT startup | AOT startup | All routes answer under AOT |
|---|---|---:|---:|---:|---:|---|
| PlainAot | yes | 0 | 10.3 MB | 263 ms | 71 ms | yes |
| CseGeneratedAot | yes | 0 | 10.4 MB | 274 ms | 72 ms | yes |
| CseReflectionAot | yes | 4 (IL2026 ×2, IL3050 ×2) | 10.0 MB [1] | 267 ms | 68 ms [1] | no: POST 404, DELETE 405 |
| CarterAot | yes | 8 (IL2026 ×3, IL2072 ×4, IL3002 ×1) | 9.1 MB [1] | 270 ms | crashed at startup | no |
| FastEndpointsAot | yes | 4 (IL2026 ×2, IL3050 ×2) | 13.7 MB [1] | 316 ms | crashed at startup | no |
| FastEndpointsSourceGenAot | yes | 0 | 15.2 MB | 319 ms | 81 ms | yes |

[1] The binary does not serve all three routes, because trimming removed code the library reaches only by reflection. Its size and startup are not comparable with the working variants.

- CseReflection is the opt-in scanner. It carries `[RequiresUnreferencedCode]`/`[RequiresDynamicCode]`, and the warnings point at that call site.
- Carter crashed with "A suitable constructor for type 'GetUserModule' could not be located". Carter documents no Native AOT approach.
- FastEndpoints with reflection discovery crashed with "The endpoint [GetUser] should either override the Configure() method or decorate the class with a [Http*(...)] attribute!". FastEndpoints documents AOT only together with the Generator, which is the FastEndpointsSourceGenAot row.
- All six variants pass the route check under JIT (POST 201/400, DELETE 204).

## Caveats

- **Machine load.** The runs shared the machine with a desktop session (load average 2.8-3.9). CseGenerated and CseReflection run the same request pipeline, yet their throughput differs by 3-11% with non-overlapping error bars. Treat any throughput gap below about 10% as weak evidence, even when it falls outside error.
- **Warm startup is not like-for-like.** FastEndpoints maps each endpoint to a parameterless delegate and builds its binder, validator, object factory and setters on the first request. That work is outside the warm unit and inside the cold one.
- **Cold allocation.** BenchmarkDotNet's MemoryDiagnoser measures allocation in a separate run, not in the timed cold launch. The allocation column is managed allocation for one invocation of the unit.
- **RDG off in BenchmarkDotNet runs.** The JIT benchmarks do not enable the Request Delegate Generator, so Plain, CSE and Carter pay RequestDelegateFactory at startup. The large-N cold gap to FastEndpoints may change with RDG on; this was not measured.
- **Validation engines differ.** Plain and CSE use DataAnnotations + `AddValidation()`; Carter and FastEndpoints use FluentValidation. The POST rows compare complete stacks, not routing alone. They exist on net10 and net11 only.
- **Ties.** A difference within the sum of the two error margins is reported as a tie.
- **Units across TFMs.** The net11 warm Baseline is 0.52 ms against about 1.14 ms on the other TFMs, so vs-Baseline ratios are not comparable across TFMs. None are quoted here.
- **Carter granularity.** One module per endpoint, matching CSE's one type per endpoint. Carter apps that group many routes per module would build fewer modules.
- **AOT startup** is median of 5 with three routes on a loaded machine. Rerun it on a quiet machine before quoting the startup column.

## How to Reproduce

```bash
cd benchmarks
./run-benchmarks.sh --project endpoints                 # all TFMs, cold + warm startup + throughput
./run-benchmarks.sh --project endpoints --quick         # net10 only, Short job
./endpoints-aot/run-aot.sh                              # Native AOT report (all six variants)
python3 CSharpEssentials.Endpoints.Benchmarks/generate-endpoints.py   # regenerate the N=10/100/500 endpoint libraries
```

Results are stored per framework under `benchmarks/results/endpoints/{tfm}/results/` (GitHub Markdown, CSV, JSON and HTML). The AOT report is `benchmarks/results/endpoints/aot/aot-report.md`; raw publish and run logs are written to `benchmarks/results/endpoints/aot/logs/`.
