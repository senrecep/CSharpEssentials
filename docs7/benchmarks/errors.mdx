title: "CSharpEssentials.Errors: performance benchmarks"
---

The CSharpEssentials.Errors (CSE) `Error` type against ErrorOr 2.1.1 and FluentResults 4.0.0, and CSharpFunctionalExtensions 3.7.0 where it has a matching API: creating an error, equality and hashing, building an error from an exception, metadata and record `ToString`, and System.Text.Json. BenchmarkDotNet v0.14.0, .NET 8, 9, 10 and 11.

The competitors are pinned exactly in `Directory.Packages.props`. Each pin is the latest stable release on NuGet as of 2026-11-03:

| Package | Version | License |
|---|---|---|
| ErrorOr | 2.1.1 | MIT. The nuspec has no license element; the repository `LICENSE.md` is MIT |
| FluentResults | 4.0.0 | MIT (nuspec expression) |
| CSharpFunctionalExtensions | 3.7.0 | MIT (nuspec expression) |

net8.0 runs CSE's netstandard2.1 build, because Errors has no net8.0 target.

Sequence, CombineAll, Try and TryAsync live in the same suite but measure Results APIs. They are described in [CSharpEssentials.Results/BENCHMARKS.md](/benchmarks/results#sequence-combineall-try-and-tryasync). The Maybe collection helpers are in [CSharpEssentials.Maybe/BENCHMARKS.md](/benchmarks/maybe).

## What was measured

The code is in `benchmarks/CSharpEssentials.Results.Comparison.Benchmarks/`, in six classes.
- Every class has `[MemoryDiagnoser]`, and CSE is the baseline in each category.
- Each class checks parity in `[GlobalSetup]`. `--self-check` runs the same check for every parameter value without BenchmarkDotNet, for these classes and the other classes in the suite. A mismatch fails the run.
- Every row returns its result, so the JIT cannot drop the work. Inputs are read from instance fields and built in setup.
- Each library row has a comment above it with its README or source URL. CSE links point at main, and competitor links point at the pinned tag. Hand-written rows have none.
- Shared inputs: code `Order.Invalid`, message `Order is invalid`. Metadata has three entries, `OrderId = 42`, `Field = "Total"` and `Attempt = 3`, added in the same order for every library. The values are boxed once and shared.

| # | Class | Measured unit | Rows | Label |
|---|---|---|---|---|
| 1 | `ErrorFactoryComparison` | `Plain`: 16 errors from 16 prebuilt code and message pairs per op, written into a sink array (`OperationsPerInvoke = 16`). `WithMetadata`: one error with the three entries | CSE `Error.Validation`, ErrorOr `Error.Validation`, FluentResults `new Error(message)` and `WithMetadata` | CSE vs ErrorOr like-for-like. FluentResults labelled: no code or type |
| 2 | `ErrorEqualityComparison` | `Equals` on two equal errors built from distinct string instances, `GetHashCode`, and `new HashSet<Error>` over 100 errors (10 codes, 10 copies each). `WithMetadata` = false or true | CSE, ErrorOr | like-for-like |
| 3 | `ErrorExceptionComparison` | an error from an `InvalidOperationException("boom")`. `Thrown` = true (thrown and caught once in setup) or false (never thrown) | CSE `Error.Exception(ex)` (baseline), CSE `Error.Failure(type name, message)`, ErrorOr `Error.Failure(type name, message)`, FluentResults `new ExceptionalError(ex)` | labelled, see below |
| 4 | `ErrorMetadataToStringComparison` | `ErrorMetadata.ToString()` with `Entries` = 1, 8 or 32 | CSE (baseline), a hand-written `StringBuilder` loop over the same dictionary | like-for-like, exact text |
| 5 | `ErrorToStringComparison` | `ToString()` on an error, an error with metadata, and a success `Result<int>` of 42 | CSE, ErrorOr, FluentResults; CFE in the `Result` category | `Error`: CSE vs ErrorOr like-for-like. The rest labelled |
| 6 | `ErrorJsonComparison` | `Serialize` and `Deserialize` of an error without metadata, one shared `JsonSerializerOptions` with default settings | Serialize: CSE, ErrorOr. Deserialize: CSE only | Serialize like-for-like, exact text |

In `ErrorEqualityComparison` the two errors use distinct code and message strings, but their metadata shares the same key strings and the same boxed values. Key lookups and value comparisons can then succeed on a reference check, for both libraries alike, so the metadata rows are a best case.

CSharpFunctionalExtensions has no column in classes 1 to 4 and 6. Its default error is a `string`, so there is nothing to construct, compare or serialize.

### Parity keys

- Factory: code, type, message and metadata entries in order for CSE and ErrorOr; message and metadata for FluentResults. FluentResults always has an empty metadata dictionary, which the key treats as no metadata.
- Equality: `Equals` gives `True` for both libraries, each library gives the same hash for its two equal errors, and both HashSets hold 10 items.
- Exception: every row has the message `boom`. The CSE rows have code `InvalidOperationException` and type `Failure`. `Error.Exception` has the metadata keys `exceptionType`, `exceptionStackTrace` and `exceptionMessage`. Stack text is never compared.
- Metadata `ToString`: exact string equality, for example `[{ key0: 0 }]`.
- `ToString`: CSE and ErrorOr give the same text for an error without metadata. The other rows only have to contain the message, or `42` for the result rows.
- JSON: CSE and ErrorOr give the same text. CSE deserializes back to an equal error.

## Semantic differences

- FluentResults errors are classes with no code or type. `new Error(message)` allocates the error, an empty metadata dictionary and an empty reasons list.
- No FluentResults equality column. FluentResults `Error` uses reference equality, so `Equals` is false and a HashSet keeps all 100 items.
- `Error.Exception` does more work than the other rows. It builds a three-entry metadata dictionary with the type name, the stack trace string and the message. When the exception was never thrown, `StackTrace` is null and the entry holds null. On a thrown exception, reading `StackTrace` formats the trace again on every call.
- ErrorOr has no exception bridge. Its row maps the type name and message by hand, as the README's section on replacing exceptions suggests. The CSE `Error.Failure` row does the same, so it shows CSE without the exception metadata.
- FluentResults `ExceptionalError` keeps a reference to the exception and copies nothing.
- `ToString` output differs. CSE and ErrorOr `Error` are record structs, and without metadata both print `Error { Code = Order.Invalid, Description = Order is invalid, Type = Validation, NumericType = 2, Metadata =  }`. With metadata, CSE formats each entry, ErrorOr prints the dictionary type name, and FluentResults joins the entries with `; `. On a success result, CSE prints `Success: 42` (the value formatted through `IFormattable` with the invariant culture), and every other library prints its own text.
- Deserialize is CSE only. System.Text.Json does not throw. It silently returns a `default` ErrorOr `Error` with a null code. FluentResults throws `NotSupportedException`, and its README says not to serialize its result objects. The serialize rows use no metadata, because a CSE round trip with metadata does not give back an equal error.

## Feature matrix

This table comes from reading each library's source and docs. None of it was measured.

| Feature | CSE | ErrorOr 2.1.1 | FluentResults 4.0.0 | CSharpFunctionalExtensions 3.7.0 |
|---|---|---|---|---|
| Error kind | struct (code, description, type, metadata) | struct (same shape) | class (message, metadata, reasons) | `string` by default |
| Typed categories | 8 `ErrorType` values | 7, plus `Custom(int)` | none | none |
| Metadata | `ErrorMetadata : Dictionary<string, object?>` with fluent `AddMetadata`, which keeps the first value for a key | `Dictionary<string, object>` | `WithMetadata`, which throws on a duplicate key | none |
| Value equality | yes, including metadata | yes, including metadata | no (reference) | string equality |
| Hash with metadata | independent of insertion order | depends on insertion order | reference | n/a |
| Exception bridge | `Error.Exception(ex)` copies type, stack trace and message | none | `ExceptionalError` keeps a reference | `ex.Message` |
| `ToString` | record output with formatted metadata | record output with the dictionary type name | `Error with Message='...'` | the string |
| System.Text.Json serialize | yes | yes, same text without metadata | yes, but the README advises against serializing result objects | n/a |
| System.Text.Json deserialize | yes; metadata values come back as `JsonElement` | silently `default` | throws | n/a |
| License | MIT | MIT | MIT | MIT |

## Results

All tables: mean and allocated bytes per operation, net10 unless stated. "Ratio" is the report's Ratio column (library mean divided by CSE mean; above 1.00 = slower than CSE). A `-` in the report's Allocated column is written as `0 B`.

### How these numbers were produced

- Full BenchmarkDotNet default-job runs (no `--quick`) on net8.0 (.NET 8.0.30, CSE netstandard2.1 build), net9.0 (9.0.19), net10.0 (10.0.11) and net11.0 (11.0.0), on a 6-core, 12-thread x64 desktop CPU on Linux, SDK 11.0.100-rc.1.26425.128, BenchmarkDotNet v0.14.0.
- 1-minute load average at the start and end of the comparison suite: 1.55 to 2.37, with a desktop session running. No row of the six Error classes stayed above 5% CV.
- `ErrorEqualityComparison` and `ErrorMetadataToStringComparison` were rerun on 2026-11-07 on .NET 8.0.33, 9.0.22, 10.0.14 and 11.0.0 with SDK 11.0.100-rc.3.26522.148. Their numbers below come from that rerun, and no rerun row is above 5% CV.
- Reports: `benchmarks/results/results-comparison/{tfm}/results/`, for example [ErrorEqualityComparison net10](https://github.com/senrecep/CSharpEssentials/blob/main/benchmarks/results/results-comparison/net10.0/results/CSharpEssentials.Results.Comparison.Benchmarks.ErrorEqualityComparison-report-github.md).

### 1. Error factory

| Row | Plain (per error) | Plain ratio | WithMetadata | WithMetadata ratio |
|---|---|---:|---|---:|
| CSE `Error.Validation` | 5.771 ns / 0 B | 1.00 | 64.585 ns / 216 B | 1.00 |
| ErrorOr `Error.Validation` | 5.280 ns / 0 B | 0.91 | 60.802 ns / 216 B | 0.94 |
| FluentResults `new Error` (labelled) | 28.055 ns / 152 B | 4.86 | 68.929 ns / 288 B | 1.07 |

CSE and ErrorOr build the same struct shape and allocate the same bytes. ErrorOr is faster on net10 by 0.491 ns plain and 3.783 ns with metadata. On the other TFMs: plain 10.269 vs 6.711 ns (net8, CSE loss), 5.307 vs 5.302 ns (net9, tie), 5.310 vs 5.576 ns (net11, CSE faster); with metadata 82.096 vs 81.072 ns (net8), 73.326 vs 80.612 ns (net9, CSE faster), 62.005 vs 59.101 ns (net11).

- `Equals` is a tie or a CSE win on every TFM except net9 without metadata, where ErrorOr is 0.288 ns faster (8.517 vs 8.805 ns).

### 3. Error from an exception

| Row | Never thrown | Thrown in setup | Ratio (thrown) |
|---|---|---|---:|
| CSE `Error.Exception(ex)` | 66.286 ns / 216 B | 2,719.927 ns / 4720 B | 1.000 |
| CSE `Error.Failure(type name, message)` | 5.215 ns / 0 B | 5.215 ns / 0 B | 0.002 |
| ErrorOr `Error.Failure(type name, message)` | 5.229 ns / 0 B | 5.215 ns / 0 B | 0.002 |
| FluentResults `new ExceptionalError(ex)` | 26.358 ns / 160 B | 26.918 ns / 160 B | 0.010 |

`Error.Exception` is the slowest row on every TFM, by design: it copies the type name, the stack trace text and the message into a metadata dictionary. On a thrown exception the stack trace text dominates (3,479.46 ns on net8, 3,131.51 ns on net9, 2,719.927 ns on net10, 2,603.245 ns on net11, 4720 B on all four). When only the code and message are needed, CSE `Error.Failure` costs about the same as ErrorOr on net9 to net11 (5.215 vs 5.229 ns on net10; on net9 thrown, 12.58 vs 16.18 ns). On net8 (netstandard2.1 build) it is slower than ErrorOr: 17.94 vs 13.32 ns never thrown, 18.55 vs 13.31 ns thrown.

| Entries | CSE | Hand-written `StringBuilder` loop | Ratio |
|---:|---|---|---:|
| 1 | 64.54 ns / 152 B | 50.09 ns / 152 B | 0.78 |
| 8 | 417.69 ns / 776 B | 264.38 ns / 776 B | 0.63 |
| 32 | 1,399.05 ns / 2400 B | 812.07 ns / 2400 B | 0.58 |

CSE loses to the hand-written loop in time at every size and TFM: the hand-written ratio is 0.54 to 0.91 on net9 to net11 and 0.32 to 0.55 on net8 (32 entries on net8: 2,561.28 ns vs 827.38 ns). Both allocate the same bytes at every size and TFM. Both grow about linearly with the entry count. CSE formats each entry straight into one builder with an interpolated `Append` and the invariant culture; the hand-written loop appends the pieces to one builder. The net8 column runs the netstandard2.1 build, which formats each entry through `AppendFormat`.

| Row | net8 | net9 | net10 | net11 |
|---|---|---|---|---|
| CSE `Serialize` | 341.1 ns / 272 B | 289.8 ns / 272 B | 280.2 ns / 272 B | 243.8 ns / 272 B |

### Where CSE loses

- Factory: ErrorOr plain on net8 (6.711 vs 10.269 ns) and net10 (5.280 vs 5.771 ns, under 1 ns); ErrorOr with metadata on net8, net10 and net11 (net10 60.802 vs 64.585 ns).
- `GetHashCode`: ErrorOr on net8, net9 and net11 without metadata (net8 28.300 vs 32.818 ns) and on net10 with metadata (66.331 vs 82.964 ns).
- `HashSet`: ErrorOr on every TFM without metadata (net10 7,111.568 vs 10,342.030 ns) and on net10 and net11 with metadata.
- `Equals`: ErrorOr without metadata on net9 by 0.288 ns (under 1 ns).
- `Error.Exception`: every other row, by design (see section 3).
- `Error.Failure`: ErrorOr on net8, both inputs (17.94 vs 13.32 ns never thrown, 18.55 vs 13.31 ns thrown).
- Metadata `ToString`: the hand-written loop at every size and TFM, in time. The bytes are the same.
- `ToString`: ErrorOr on `Error` without metadata on net10 (170.33 vs 175.50 ns); ErrorOr and FluentResults on `Error` with metadata on every TFM; FluentResults on `Error` without metadata (it prints less text). CFE allocates less on the `Result` row on net8 (48 B vs 72 B).
- JSON: ErrorOr `Serialize` on net8 (321.2 vs 341.1 ns).

## Caveats

- CSE behavior was checked against the code in this tree:
  - `CSharpEssentials.Errors/Error.cs`: `GetHashCode` sums the metadata entry hashes, so two equal errors hash the same whatever the insertion order. Nested `ErrorMetadata` values are compared by value in `Equals`.
  - `CSharpEssentials.Errors/ErrorMetadata.cs`: `ToString` enumerates the dictionary once. `CreateWithExceptionDetailed` reads `exception.StackTrace` and does not walk the stack for an exception that was never thrown. `CreateWithException` stores a nested `ErrorMetadata`, not the `Exception`, so System.Text.Json can serialize it.
  - A JSON round trip of an error with metadata is not equal to the original, because the values come back as `JsonElement`.
- The `GetHashCode` net10 ErrorOr row and the `HashSet` net10 CSE row without metadata are single-TFM outliers. Both stayed outliers in the 2026-11-07 rerun of the class, with CV under 5%.
- The CSE column is the working tree, which may not match the version published on NuGet.

## How to reproduce

```bash
cd benchmarks
./run-benchmarks.sh --project results-comparison                        # all TFMs (net8-net11), default job
./run-benchmarks.sh --project results-comparison --tfm net10.0          # one TFM
./run-benchmarks.sh --project results-comparison --quick                # net9.0, Short job, one filter per class
dotnet run -c Release -f net10.0 --project CSharpEssentials.Results.Comparison.Benchmarks -- --self-check
dotnet run -c Release -f net10.0 --project CSharpEssentials.Results.Comparison.Benchmarks -- --filter "*.ErrorFactoryComparison.*"
```

Short-job numbers cannot be compared with default-job numbers. Results are stored per framework under `benchmarks/results/results-comparison/{tfm}/results/`.
