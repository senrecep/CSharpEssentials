`Guider` (namespace `CSharpEssentials.Core`) creates GUIDs and converts them to and from a 22-character URL-safe string. Every method is thread-safe.

```csharp Program.cs
// dotnet add package CSharpEssentials.Core
using CSharpEssentials.Core;

Guid id = Guider.NewGuid();
Guid ordered = Guider.NewMonotonicGuid();
Guid stamped = Guider.NewGuid(new DateTimeOffset(2025, 1, 1, 0, 0, 0, TimeSpan.Zero));
Guid sqlKey = Guider.NewSqlServerGuid();
Guid site = Guider.NewGuidV5(GuidNamespaces.Dns, "www.example.com");

Console.WriteLine(id.Version);      // 7
Console.WriteLine(sqlKey.Version);  // 8
Console.WriteLine(site);            // 2ed6657d-e927-568b-95e1-2665a8aea6a2
Console.WriteLine(stamped.ToString()[..13]); // 01941f29-7c00: the timestamp of 2025-01-01

string shortId = Guider.ToStringFromGuid(ordered);
Console.WriteLine(Guider.ToGuidFromString(shortId) == ordered); // True
```

## NewGuid()

Returns an [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562#name-uuid-version-7) version 7 GUID on every target: 48 bits of Unix time in milliseconds (big-endian), the version nibble `7`, the variant bits `10` and 74 random bits. IDs from different milliseconds sort by creation time while the system clock does not move backwards. IDs from the same millisecond have no set order.

The package builds this layout itself instead of calling `Guid.CreateVersion7()`, so a .NET 8 app (which uses the `netstandard2.1` build) gets version 7 too.

The random bits come from a per-thread pool of 1024 bytes; one refill serves 102 IDs. A refill reads 1024 bytes from `RandomNumberGenerator` (OpenSSL on Linux) and takes one `Guid.NewGuid()` as a salt, and every ID XORs the salt into its bytes. So every ID also carries fresh bits from the operating system source that `Guid.NewGuid()` and `Guid.CreateVersion7()` read. `Guid.CreateVersion7()` reads the generator for every ID, which on Linux costs about 0.8 to 1 µs on .NET 9 and .NET 10.

A call allocates nothing, except the 1024-byte pool on the first call of each thread. See [Cost](#cost).

### Cloned processes

A cloned virtual machine, or a checkpointed and restored process, starts with the same unused pool bytes as its siblings, and with the same state of any random generator inside the process, such as OpenSSL's. Three guards keep the clones apart:

- Every refill takes a new salt from `Guid.NewGuid()`, which reads the operating system on each call.
- A thread uses its pool only while it makes IDs at most 1 ms apart. The first ID after a longer pause, or after the clock steps back, takes its bits from `Guid.NewGuid()`, and that GUID becomes the salt for the rest of the pool. A snapshot taken while the thread is idle leaves each clone with its own salt.
- The clock ticks inside the millisecond (100 ns steps) are XORed into the random bits, so two clones that use the same leftover bytes still differ unless they read the clock in the same 100 ns tick.

What is left: a snapshot taken less than 1 ms after a thread made an ID, restored with a clock that still reads less than 1 ms after that ID, keeps the same salt and leftover bytes on that thread. Two such clones return the same GUID if they create an ID at the same pool position in the same 100 ns tick. At most 102 IDs per thread come from leftover bytes. After those, IDs are as safe between clones as `Guid.NewGuid()`, which depends on the operating system giving each clone fresh randomness.

If the clock is resynced before the clones run, it rarely reads within 1 ms of the last ID. A cloned VM whose clock resumes from the snapshot time does read within 1 ms by default, and its clones run the same code from the same state, so a collision is much likelier than chance. The number of pairs that can collide grows with the square of the number of clones. `Guid.CreateVersion7()` reads the operating system for every ID and has no such exposure.

Turn the pool off for any cloned VM or restored process that serves work before its clock is resynced. Set the switch before the first ID is created, in the project file:

```xml
<ItemGroup>
  <RuntimeHostConfigurationOption Include="CSharpEssentials.Guider.DisableRandomPool" Value="true" />
</ItemGroup>
```

or with `AppContext.SetSwitch("CSharpEssentials.Guider.DisableRandomPool", true)` at startup. Every ID then takes its random bits from `Guid.NewGuid()`, as `Guid.CreateVersion7()` does, and costs about the same. The switch covers `NewMonotonicGuid()` and `NewSqlServerGuid()` too.

## NewGuid(DateTimeOffset) and NewGuid(TimeProvider)

Return a version 7 GUID stamped with the given time, or with the current time of a `TimeProvider`. With `FakeTimeProvider` a test can predict the timestamp.

```csharp
Guid stamped = Guider.NewGuid(order.CreatedAt);  // order.CreatedAt is a DateTimeOffset
Guid fromClock = Guider.NewGuid(timeProvider);   // timeProvider is a TimeProvider
```

- The random bits come from `Guid.NewGuid()` on every call, not from the pool, and these overloads do not touch the state of `NewGuid()`, `NewMonotonicGuid()` or `NewSqlServerGuid()`.
- IDs with the same timestamp have no set order.
- A time before 1970-01-01T00:00:00Z throws `ArgumentOutOfRangeException`. A `null` provider throws `ArgumentNullException`.
- The `TimeProvider` overload exists in the .NET 9 and later builds. The `netstandard2.0` and `netstandard2.1` builds (used by .NET 8 and .NET Framework apps) have only the `DateTimeOffset` overload; pass `timeProvider.GetUtcNow()` there.
- Since 9.0 an XML doc reference must name the overload: `<see cref="Guider.NewGuid()"/>`. A bare `Guider.NewGuid` is CS0419.

## NewGuidV5(namespace, name)

Returns the [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562#name-uuid-version-5) version 5 GUID of a name in a namespace: the SHA-1 of the namespace bytes followed by the name bytes, with the version and variant bits set. The same namespace and name give the same GUID on every target and in every process, so an ID can be derived from a natural key instead of stored.

```csharp
Guid site = Guider.NewGuidV5(GuidNamespaces.Dns, "www.example.com"); // 2ed6657d-e927-568b-95e1-2665a8aea6a2
Guid raw = Guider.NewGuidV5(GuidNamespaces.Oid, "1.3.6.1"u8);       // ReadOnlySpan<byte>, hashed as given
```

The string overload hashes the UTF-8 bytes of the name, throws `ArgumentNullException` for `null` and `ArgumentException` for a lone surrogate. `GuidNamespaces` holds the four namespaces the RFC defines (`Dns`, `Url`, `Oid`, `X500`); any GUID works as a namespace of your own. SHA-1 is what the RFC defines for version 5: the GUID names something and is not a secret. `IdempotencyKeys.ToUuidV5` in `CSharpEssentials.Idempotency` uses this method.

## NewMonotonicGuid()

Returns a version 7 GUID that is greater than every GUID it returned before in the same process (per loaded copy of the assembly), compared as big-endian bytes, with `Guid.CompareTo` or as strings.

```csharp
Guid first = Guider.NewMonotonicGuid();
Guid second = Guider.NewMonotonicGuid();
// second.CompareTo(first) > 0, even inside the same millisecond
```

The 12 bits after the version (`rand_a` in RFC 9562) hold the time inside the millisecond in steps of 1/4096 ms (RFC 9562 section 6.2, method 3). The first 6 bits of `rand_b` hold a counter (method 1). The timestamp, fraction and counter are packed into one number. A new ID starts from the current time with the counter at 0. If that is not greater than the last packed value (another ID took the same 1/4096 ms step, or the clock stalled or went back), the ID takes the last value plus one. A counter overflow carries into the fraction, and a fraction overflow into the timestamp. The shared value is updated with `Interlocked.CompareExchange`, without a lock. Random bytes come from the same per-thread pool as `NewGuid()`, with the same guards for cloned processes, so the call allocates nothing.

Trade-offs:

- Each ID has 56 random bits instead of 74: the counter takes 6 bits of `rand_b`.
- All threads update one shared value. With 6 threads it cost 28 to 31 ns per ID in a quick benchmark, against 12.5 to 16.5 ns for `NewGuid()`. See [Cost](#cost).
- The order holds within one process and one loaded copy of the assembly. Two `AssemblyLoadContext`s or .NET Framework AppDomains each keep their own value, and two processes or machines can produce IDs that interleave.
- The fraction and counter allow 262,144 IDs per millisecond (64 in each 1/4096 ms step), about 262 per microsecond across all threads. In a test, 1,000,000 IDs from a tight loop kept the encoded timestamp within 1 ms of the clock. Above that rate the encoded timestamp runs ahead of the clock, by roughly (IDs / 262,144) ms minus the elapsed time, and catches up once the rate drops. A clock that goes back keeps the timestamp at the last value until the clock passes it.
- The counter starts at 0 in each step, so it shows how many IDs the process made in that 1/4096 ms.

Use `NewGuid()` when IDs only need to be unique and roughly time ordered. Use `NewMonotonicGuid()` when code relies on the creation order of IDs from one process, for example a cursor or an append-only log.

## Cost

Time per ID from a quick BenchmarkDotNet ShortRun on a 6-core, 12-thread x64 desktop CPU on Linux, 1-minute load average 1.3 to 4.7. Every row allocated 0 bytes. The .NET 8 column runs the `netstandard2.1` asset, and .NET 8 has no `Guid.CreateVersion7()`. The 6-thread rows run 6 threads that each make 20,000 IDs.

| Method | .NET 8 | .NET 9 | .NET 10 | .NET 11 |
|---|---:|---:|---:|---:|
| `Guid.NewGuid()` (version 4) | 766 ns | 759 ns | 739 ns | 59 ns |
| `Guid.CreateVersion7()` | n/a | 801 ns | 782 ns | 91 ns |
| `Guider.NewGuid()` | 71 ns | 70 ns | 60 ns | 54 ns |
| `Guider.NewMonotonicGuid()` | 84 ns | 81 ns | 75 ns | 71 ns |
| 6 threads: `Guid.NewGuid()` | 152 ns | 152 ns | 151 ns | 12.7 ns |
| 6 threads: `Guid.CreateVersion7()` | n/a | 164 ns | 159 ns | 18.7 ns |
| 6 threads: `Guider.NewGuid()` | 16.5 ns | 15.7 ns | 14.0 ns | 12.5 ns |
| 6 threads: `Guider.NewMonotonicGuid()` | 30.6 ns | 29.2 ns | 27.8 ns | 28.2 ns |

On .NET 8, 9 and 10 the BCL reads the operating system once per GUID, so the pool makes an ID 11 to 13 times cheaper on one thread and 9 to 11 times cheaper with 6 threads. On .NET 11 the BCL read is much cheaper, and `Guider.NewGuid()` is still faster than `Guid.CreateVersion7()`.

These rows come from tight loops. The first ID after a pause of more than 1 ms takes the `Guid.NewGuid()` path, so a thread that makes a few IDs at a time pays about what `Guid.CreateVersion7()` costs for the first one. In a Stopwatch probe that paused 1.5 ms before each burst, `Guider.NewGuid()` was within about 15% of the BCL for bursts of one ID on .NET 8, 9 and 10 and faster from two IDs on. On .NET 11 it was about 10 ns slower for bursts of one ID, about equal at two, and faster from three on. Bursts of one or two IDs on .NET 11 timed very differently from run to run on the test machine, so treat those two rows as close to even.

## NewSqlServerGuid()

Version 7 GUIDs are ordered when compared byte by byte from the first byte, which is how `Guid.CompareTo`, PostgreSQL `uuid` and string sorting compare them. SQL Server's `uniqueidentifier` compares the last 6 bytes first ([Comparing GUID and uniqueidentifier values](https://learn.microsoft.com/sql/connect/ado-net/sql/compare-guid-uniqueidentifier-values)). Those bytes are random in a version 7 GUID, so neither `NewGuid()` nor `NewMonotonicGuid()` gives sequential index order in a SQL Server `uniqueidentifier` column.

`NewSqlServerGuid()` returns an RFC 9562 version 8 GUID laid out for that order: the Unix milliseconds sit big-endian in the last 6 bytes, and the time inside the millisecond and the counter of `NewMonotonicGuid()` follow in the bytes SQL Server compares next. Each value is greater than the previous `NewSqlServerGuid()` value from the same process in `SqlGuid` order, and it carries 56 random bits. It does not sort by time anywhere else, so use it only for SQL Server columns. `UseOrderedGuidKeys()` in the EntityFrameworkCore package uses it on SQL Server.

## ToStringFromGuid and ToGuidFromString

`ToStringFromGuid` writes a GUID as 22 characters of RFC 4648 base64url without padding: standard Base64 with `+` replaced by `-` and `/` replaced by `_`. Any base64url decoder, such as `System.Buffers.Text.Base64Url`, returns the same GUID. `ToGuidFromString` reads it back from a `string` or a `ReadOnlySpan<char>`. On .NET 9 and later both use `Base64Url`; the other targets work on stack buffers.

```csharp
Guid id = Guider.NewGuid();
string shortId = Guider.ToStringFromGuid(id);   // for example "Yx7A9bx0T0y2zKl3mN8pQw"
string same = id.ToStringFromGuid();            // extension form

Guid parsed = Guider.ToGuidFromString(shortId);
Guid sameId = shortId.ToGuidFromString();       // extension form
```

The input must be exactly 22 characters from `A-Z`, `a-z`, `0-9`, `-` and `_`. Any other length or character throws `FormatException`. There is no `TryParse` form, so catch `FormatException` for untrusted input. The last character carries 2 data bits and 4 unused bits. A last character with non-zero unused bits decodes to the same GUID as the canonical one on every runtime, and `ToStringFromGuid` always writes the canonical character.

## Upgrading to 8.0

- On `netstandard2.0` and `netstandard2.1` (so on .NET 8 and .NET Framework), `NewGuid()` returns version 7 GUIDs instead of random version 4 GUIDs. The first 6 bytes show when the ID was created; use `Guid.NewGuid()` if an ID must not reveal that.
- On every target `NewGuid()` builds the GUID from the per-thread pool instead of calling `Guid.CreateVersion7()` on .NET 9 and later. For cloned VMs and restored processes read [Cloned processes](#cloned-processes); the `CSharpEssentials.Guider.DisableRandomPool` switch restores one OS read per ID.
- `ToStringFromGuid` and `ToGuidFromString` use the RFC 4648 base64url alphabet; 7.x used the reverse mapping. The [package README](/libraries/core#upgrading-to-80) shows how to convert stored IDs.
